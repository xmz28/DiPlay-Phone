# 雅迪仪表与 CarPlay 融合显示方案

2026-10-13。第一阶段显示在 Redmi K30 安卓手机，后续再研究向原车 TFT 转发。

## 结论与能力边界

现有项目适合先实现安卓本地仪表与 CarPlay 导航融合的驾驶页面，同时保留完整 CarPlay 页面。可以采用全屏背景、边缘仪表、统一留白与页面过渡，避免小窗视觉。

这属于接收端本地合成。真正的 CarPlay Ultra 还包括车辆专用资源包、本地渲染脚本、车辆状态接口和 UI sync。当前仓库的上游说明只声明 Ultra 触发能力，明确协议栈未测试/未完成；不能将现有普通主屏/仪表副屏支持当成 Ultra 完整实现。

普通 CarPlay 视频流提供已经合成的画面。接收端不能随意分离 iPhone 的地图、电话弹窗、音乐卡片等元素。地图副屏可用于仪表融合，但不能取代完整 CarPlay 的全部交互。

## 已核实的项目基础

### MyApplication

- 实际数据入口是 `Esp32VehicleBleClient`；状态模型为 `VehicleState`。
- 协议文档定义 20 Hz 实时包及 1 Hz 全量包，客户端分别解析并合并。
- `HmiDashboardView` 使用 Android Canvas 绘制，800×480 是设计坐标，通过比例适配实际 View。
- 仪表背景、速度/模式、右侧功率信息、底部指标已有分开的绘制函数。
- 当前 `onDraw` 先画黑色和完整背景，不能直接覆盖在地图上，否则会遮住地图；需要拆出透明仪表前景与独立背景。
- `VehicleState.toDashboardData()` 中转速为 `speedKmh * 72`，总里程为 `1186.0`，电压/电流为零；这些不是已经获取到的真实车辆值，后续需映射真实字段或标记未提供。

### DiPlay-Phone

- 主屏使用 MediaCodec 解码到 TextureView，并负责触摸转发。
- 已有仪表副屏类型 111，支持地图/转向卡片，并有虚拟副屏配置。
- 虚拟副屏代码默认 1280×720；这是既有配置，不是新方案的最终目标分辨率。主屏与融合页面应以实际显示尺寸及解码能力为依据。
- 需要先验证当前 iPhone/红米组合的副屏地图建立、稳定播放及主副屏切换；源码存在不能代替设备验证。

### bleconnect

- 现有投屏链路为 TCP 控制 8888、UDP 图片 8889，发送 JPEG。
- 实时帧目标间隔 100 ms，即目标 10 FPS，不等于实测帧率，也不是已验证的设备极限。
- `bitmapToMirrorJpeg()` 会按仪表画布比例居中裁剪源图。未来转发组合界面时应直接按协商尺寸合成，避免裁掉速度或指示灯。
- 现有网络代码包含进程级绑定和单 socket 绑定。后续与 CarPlay 无线同时运行时，需隔离网络路由并验证 Wi-Fi 并发，不能直接将两套自动连接代码合并。
- 第一阶段不需要引入截图、JPEG 或原车 Wi-Fi 投屏链路。

## 推荐的页面组织

### 驾驶融合页面

导航地图作为连续背景或主体，车辆状态在前景本地绘制。

- 顶部：转向、远近光、故障、连接状态等窄状态带。
- 左侧约 30%：突出车速、档位/模式及功率，不照搬完整 800×480 仪表并缩小。
- 右侧约 70%：仪表副屏地图与导航指引；用统一背景、留白、渐变衔接，不加可拖动小窗边框。
- 底部：电量、里程及其他次要信息。
- 将地图关键内容的安全区设置在实际可见区域，避免车标或指引被仪表遮住。安全区不是图像透明通道。
- 页面切换时由安卓统一控制仪表位置和地图容器的变化；不能承诺同步 iPhone 内部每个元素的动画。

### 完整 CarPlay 页面

显示电话、音乐、第三方导航和 CarPlay 应用列表。车辆信息可收成固定窄栏，并按剩余画布配置主屏与触摸映射；也保留完全铺满 CarPlay 的选项。显示尺寸变更是否需要重新连接，应结合现有协议实测，不能承诺随时无缝重排 iPhone UI。

### 纯仪表页面

iPhone 未连接时继续使用本地车辆数据。数据失效应标记断开/未知，不能默认切换成演示车速。

## 渲染实施

首版可使用同一 Activity 内的 FrameLayout：背景 → 导航 TextureView → 透明仪表 View → 本地操作区域。Android 图形系统合成，不需要系统悬浮窗或 root。

MediaCodec 直接输出到 Surface，避免每帧 TextureView.getBitmap、CPU 拷贝和 JPEG 编码。复用仪表 PNG、Paint 和静态背景，数据接收与绘制解耦，只保留最新状态。

以稳定 60 Hz 绘制为初始目标并测量实际帧率、掉帧、数据到画面延迟与解码成本。20 Hz 车辆输入不等于仪表动画只能 20 FPS；指针/布局动画可以按显示帧更新，数字和指示灯保留最新真实状态。不能用插值生成并不存在的车辆测量值。

需要复杂遮罩、多输出和后续转码时，再考虑专门的 EGL/OpenGL 合成器。自建合成器可以管理本地图层与视频纹理，但不会自动获得 Ultra 的资源包与 UI sync 能力。

## 分阶段验证

1. 先在 K30 验证仪表副屏地图。若当前组合无法输出，先用完整主屏与固定仪表区的方案，不裁切主屏伪装成纯地图。
2. 将现有仪表拆为可复用数据源与透明前景，搭建驾驶融合页面。使用测试数据时明确标记，随后接入现有 BLE 实时数据。
3. 保留完整 CarPlay 与纯仪表页面，验证触摸、Home、断开重连和数据过期处理。
4. 测量主/副屏解码、绘制帧率、功耗温度，以及 BLE 与无线 CarPlay 同时工作的稳定性。
5. 以后转发原车 TFT 时，再决定安卓合成整帧或 TFT 本地绘制车辆前景。当前 JPEG 协议没有证明独立透明图层、区域更新或双层动画同步能力，必须查看接收端协议/固件。
